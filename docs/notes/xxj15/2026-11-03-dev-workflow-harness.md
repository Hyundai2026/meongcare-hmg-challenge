## 무엇을 했나

계획 → 구현 → 테스트 → 확인 → 노트로 이어지는 작업 흐름을 규칙으로 만들었다. 무엇을 쓰면 되는지는 사람과 Claude 모두 [CLAUDE.md](../../../CLAUDE.md)의 "작업 흐름" 하나만 보면 된다.

## 어떻게: 핵심 결정과 이유

- **Claude는 단위마다 자동으로 커밋한다.**
  - 이유: 작업을 다 하고 나서 쪼개면 섞인 변경을 나누기 어렵다. 처음부터 작게 커밋하는 게 확실하다.
  - push와 PR은 사람이 정한다.
- **기능 브랜치 + PR을 쓰고, 머지는 merge commit으로 한다.**
  - 이유: squash로 머지하면 잘게 나눈 커밋이 하나로 합쳐진다.
- **노트는 `docs/notes/<git user.name>/YYYY-MM-DD-<작업>.md`에 둔다.**
  - 팀원별 노트와 작업별 노트를 둘 다 원해서, 팀원 폴더 아래에 작업별 파일을 두는 구조로 합쳤다.
- **빌드 훅을 `stop-verify.mjs`에서 `build-gate.mjs`로 바꿨다.**
  - 기존 훅은 커밋 안 된 변경만 봤다. 그래서 턴 중에 커밋하면 검사를 건너뛰었다.
  - 이제는 작업 트리에 있는 앱 코드 전체의 내용으로 해시를 만든다.
  - 커밋 직전 검사(PreToolUse)를 추가했다:
    - main에 직접 커밋하면 막는다.
    - 앱 코드가 들어가는 커밋은 빌드가 통과해야 진행된다.
- **문서만 바뀐 커밋은 빌드하지 않는다.**
  - 스테이징된 파일로 판단한다.
  - 같은 명령 안에서 `git add`나 `commit -a`를 쓰면 아직 스테이징 전이다. 이때는 바뀐 앱 코드가 있으면 커밋에 들어간다고 보고 빌드한다.
- **커밋과 PR에 Claude 트레일러를 붙이지 않는다.**
  - `attribution` 설정을 빈 값으로 둬서 자동으로 붙지 않게 했다.
  - 설정은 Claude가 메시지에 직접 써 넣는 경우까지 막지 못한다. 그래서 커밋 직전 훅에서도 차단한다.
- **`tester`에게는 계획 파일과 대상만 넘긴다.**
  - 구현 설명을 같이 주면 구현에 맞춘 테스트를 쓰게 된다. 계약을 기준으로 쓰게 하려는 것이다.

## 확인

- `build-gate.mjs`: 임시 저장소에서 가짜 `gradlew`로 16개 시나리오를 돌려 모두 기대대로 동작했다. 주요 시나리오:
  - main 차단
  - 빌드가 실패하면 커밋 차단
  - 턴 중 커밋 후 Stop에서 빌드
  - 문서 커밋은 빌드 생략
  - `secrets.properties`는 해시에서 제외
- 커밋 명령 판별 정규식: 커밋 명령 형태 7개로 확인했다.
  - `git -c`·`git -C` 옵션, `--amend`, `git add && git commit` 한 줄, `commit-tree` 제외
- 실제 저장소에는 아직 `gradlew`가 없다. 그래서 진짜 Gradle 빌드와 함께 돌려보지는 못했다.

## 주의점 / 남은 일

- Android 프로젝트를 만든 뒤 처음 커밋할 때, 실제 `assembleDebug`로 커밋 게이트가 동작하는지 한 번 확인한다.
- 커밋 메시지 형식은 문서로만 정해져 있고, 훅이 검사하지는 않는다.
- 훅은 Claude의 커밋에만 걸린다. 사람이 main에 커밋하는 것까지 막으려면 GitHub 브랜치 보호 규칙을 켠다.
  - (같은 날 변경) PR을 쓰지 않게 되어 "Require a pull request"는 켜지 않는다. 지금 기준은 `docs/conventions/git.md`의 "GitHub 저장소 설정"이다.
  - 대신 main push 전 검증은 pre-push 훅이 맡는다. 자세한 내용은 [2026-11-03-local-merge-flow.md](2026-11-03-local-merge-flow.md).
